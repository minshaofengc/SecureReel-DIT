发布就绪度评估

SecureReel DIT

版本 1.0.0 评估日期 2026 年 9 月 15 日 基于当前代码全量审查

内功很扎实，但外壳还没穿好——现在这东西能给你自己用，还不能给你剧组里的 DIT 用。

代码本身的质量超出预期：337 项测试全过、类型检查和代码规范零报错、拷贝引擎"源盘只读一遍"的架构是对的、 合规红线守得很干净。这些是最难做对的部分。

但"发布"需要的是另一层东西：一个能让别人双击打开的安装包。 我实际跑了打包：第一次失败（卡在下载运行环境），把下载源换成国内镜像后——38 秒就产出了一个 119MB 的安装包。 所以"能不能打包"这件事本身已经通了，不算难关。

真正的问题是这个包的质量。我打开产出的成品逐项检查，发现它用的是 Electron 的默认图标、没有开发者签名、只支持 Apple 芯片、而且没带上首帧功能所依赖的 FFmpeg。 也就是说：现在能打出包，但这个包发给别人，对方会看到一个灰色原子图标、被 macOS 拦下、装完打开后报告里没有首帧图。 再加上没有 git 仓库、LICENSE 文件缺失——目前它对外的形态仍然是"开发者工程"，不是"软件"。

代码与工程优

  • 类型检查、代码规范零报错
  • 三层进程隔离严格执行（沙箱 + 上下文隔离）

P0阻断发布

这五件事不做完，就不能称任何人为"用户"。按修复优先级排列。

1. 能打出包了，但打出来的是个"裸包"已实测

我第一次执行打包是失败的。原因不在代码，而在下载：打包过程需要下载一个约 100MB 的运行环境， 本机走代理时被返回 502，不走代理时直连超时。补上两个国内镜像源之后，同样的命令 38 秒就跑完，产出了一个 119MB 的安装包。所以"打不出包"这一条，修起来其实很快。

但打包工具自己的日志，把这个包的四个硬缺口全说清楚了：

图标——日志原话是"default Electron icon is used, reason=application icon is not set"。 我打开成品确认了，包里的图标文件就是 electron.icns。用户看到的会是那个灰色的原子符号。

签名——日志原话是"skipped macOS application code signing"。 成品只有系统自动附加的临时签名（ad-hoc），不是开发者签名，过不了 macOS 的公证检查。

架构——成品里的主程序是纯 arm64 架构，Intel 芯片的 Mac 完全装不上。

应用标识——自动生成的 com.electron.securereel-dit， 用的是一个"这是 Electron 应用"的默认前缀，而不是你自己的标识。 它会出现在系统权限列表、崩溃报告、升级识别里——看起来就像个没做完的软件。

怎么办：三件事。做一套应用图标（1024×1024 的图，打包工具能自动生成各尺寸）； 写一份打包配置（应用标识、分类、支持 Intel + Apple 双架构）； 把两个下载源的镜像写进打包命令，顺手把 Node 版本要求对齐成实际值。 这一轮做完，才第一次产出"能拿给别人"的包。

2. 分发方式需要重新定位

目前"安装"的主要方式仍然是：双击一个命令行脚本 → 它检查你有没有装 Node.js → 没装就引导你去官网下载 → 然后联网下载几百兆的依赖。

对开发者这没问题。但对现场的 DIT 和数据管理员，这条路的每一步都是死路： 片场电脑上没装开发环境、现场网络可能是共享热点、下载几百兆可能要好几分钟甚至失败。 而且这些东西跟"我要拷卡"这件事毫无关系。

现在这个项目里其实已经有两种东西了：一个给开发者的启动脚本，和一个刚打出来的安装包。 缺的不是技术，而是定位——对外发布的那一个应该只有安装包， 脚本退回去当开发者工具。一个真正能发布给别人用的 DIT 工具，流程应该是： 双击磁盘映像 → 拖进"应用程序" → 双击图标 → 开始拷卡。中间不该出现终端窗口，也不该出现 Node.js。

怎么办：把安装包做成唯一的对外交付物（不需要任何额外运行环境，运行环境已经打进包里了）。启动脚本保留，但在文档里明确标注"仅开发者使用"。

3. 没有签名和公证，用户打开就会被拦最劝退

macOS 对新软件有一道关卡：没经过苹果签名和公证的程序，用户双击时会看到 "无法打开，因为无法验证开发者"，只有到"系统设置 → 隐私与安全性"里点"仍要打开"才能绕过。

对熟悉电脑的人这只是麻烦一步。但对你的目标用户，这一屏通常的结局是： 放弃、删除、然后告诉你"你那个软件有毒"。

而且现场还有个更现实的问题：片场电脑往往不是管理员账号，用户可能连"仍要打开"的按钮都点不了。

我检查了刚打出来的那个包，它的签名状态是"临时签名（ad-hoc）"—— 这是系统在打包时自动附加的占位签名，不是开发者签名，过不了公证检查。 所以这一屏提示是必然会出现的，不是"偶尔"。

怎么办：两条路。付费路线是加入苹果开发者计划（约 99 美元/年），拿到证书做签名 + 公证，用户双击即开，体验最干净。 免费路线是在下载页明确教用户怎么绕过，但这会让一部分人直接放弃。对一个要公开给陌生人的软件，这笔钱基本是必花的。

4. 这不是一个 git 仓库已实测

我检查过，这个文件夹没有版本控制。这一条可能比前面几条更容易被忽视，但对一个要长期迭代的软件来说风险最高。

具体意味着什么：没有历史记录，改坏了没法退回上一个能跑的版本；没有分支，想试一个新做法就得赌上现有代码； 硬盘坏了就是全部丢失；想开源、想让人提问题、想协作，都没有载体。 现在整个项目只存在这一份文件里，而这是一台要用来处理客户素材的工作机。

尤其考虑到这是一个准备开源、准备给别人用的项目——没有仓库的"开源项目"是不成立的， 别人既看不到你改了什么，也没法给你反馈。

怎么办：初始化仓库，把已有的 .gitignore（已经写好了，内容是对的）用起来，提交第一版，然后推到一个私有或公开的远端。这件事花不了十分钟，但它是所有后续工作的地基。

5. 声明了 GPL 许可，但许可证正文不存在已实测

项目里写着"GPL-3.0-only"，说明书里也写了许可，但根目录没有 LICENSE 文件—— 而且 README 里引用的 LICENSE 和 THIRD_PARTY_NOTICES.md 两个文件都不存在，点了会 404。

法律上，没有许可证正文的代码处于"保留全部权利"状态：别人既没有合法权利使用它，你也没法主张别人违反 GPL。 对一个打算公开的开源项目，这是个必须补上的口子。

第三方声明文件缺失同样要紧：这个项目用到了 hash-wasm、zod、React 等开源组件， 如果以后要随包附带字体或工具，还要按各自的许可要求列明来源。

怎么办：放入 GPL-3.0 正文，写一份第三方组件清单（名称、版本、许可、来源链接）。这是发布前的机械动作，但缺了就是不规范的。

P1会让你在现场尴尬

这七件事不阻断发布，但会在别人第一次真正用它的时候冒出来。按可信度排序。

6. 视频首帧和元数据，别人装了看不到已实测

报告里最有价值的部分之一——每条素材的首帧画面、拍摄时间、时码——依赖 FFmpeg 这个独立工具。 而这台电脑上能用，只是因为你自己用 brew 装过它（我确认了它在 /opt/homebrew/bin/）。

问题在于，README 里写的是"通过随应用分发的开源 FFmpeg/ffprobe 读取"，但代码注释里明确写着"不由本应用分发"， 而且实际也没有任何 FFmpeg 二进制被打进包里。 我在刚打出来的安装包里搜过了：里面只有一个 Electron 框架自带的多媒体库（那是浏览器内核用来放视频的）， 没有可用的 FFmpeg 命令行工具。

结果就是：你把软件发给同事，他装完跑一个任务，报告里"首帧画面"那一节全是空的，元数据也全空。 他会以为软件坏了，你会以为是自己代码有问题——但其实只是他电脑上没装 ffmpeg。 这类"在我机器上好好的"最伤人。

怎么办：三选一，必须明确选一个，然后把文档改成和实际一致。 （1）真的把 FFmpeg 随包分发，需要同时处理它的许可与来源声明； （2）不分发，但把"需要自行安装 FFmpeg"写在最显眼的位置和首次运行提示里； （3）不分发，同时把首帧功能默认关掉，改成用户主动开启。 现在这种"文档说分发、代码不分发、用户不知情"是最糟的组合。

7. 设置里有一个开关是假的已实测

设置页里有一项"单目标并发文件数"，可以调 1 到 8。但我搜遍了主进程代码， 这个值从头到尾没有被读取过一次——拷贝主循环是严格的一个文件接一个文件的串行处理。

也就是说用户把它调到 8，什么都不会发生，速度一模一样。 这比"没有这个功能"更糟：用户会以为是自己没配对，或者硬件不行，然后对整台软件的可信度打折扣。

怎么办：要么把它真正接进拷贝循环（并发处理多个文件确实能提升小文件居多的卡的速度），要么先把这个开关从界面上撤掉。二选一，别留着。

8. 一个文件出错，整块盘被判"不可信"

现在的逻辑是：只要某个文件在任何一环失败（写入出错、重读校验值不符），这块目标盘就被永久标记为失败， 后续所有文件都不再往里写。

对真正的硬件故障，这个"宁可停手"的策略是合理的。但有一类情况会造成误伤： 如果目标盘上碰巧存在一个同名且大小又刚好相同的旧文件，重读校验必然对不上， 于是整块盘当场出局——而这块盘其实好得很，只是那一个文件撞名字了。

现场遇到这种情况会很难解释："为什么这个盘拷到一半不拷了？" 用户看到的是"盘坏了"。

怎么办：把失败的原因分成两类。I/O 类错误（写入失败、读取失败、校验值不符）继续按现在这样隔离整盘，这是对的； 命名冲突类（目标已有同名不同内容文件）只让那一个文件失败，盘继续用，并在任务开始时就把冲突清单列出来让用户决定。

9. 缺"只校验、不拷贝"模式

这是 DIT 日常最常用的操作之一：素材已经拷过了，现在只想验一遍目标盘完不完整—— 比如隔天复检、或者拿到别人拷好的盘要核对。

现在没有这个入口。变通办法是"建一个指向同样来源的任务、把目标设成那个盘"， 靠"目标已有同名同尺寸文件"的逻辑走校验流程——但这既绕、又不可靠，而且上面第 8 条会让它格外脆弱。

怎么办：加一个"仅校验"任务类型：选源、选要校验的目标，软件只算源侧与目标侧的校验值并比对，不写入任何一个字节。这是很多同类工具的核心功能。

10. 报告说是"离线 HTML"，但它不是单文件

报告 HTML 里引用首帧图的方式是相对路径 frames/xxx.jpg， 也就是说图片是独立文件，HTML 只负责指路。

只要把 HTML 连同 frames 目录一起拷走，它是对的； 但只要有人单独把这个 HTML 文件发到微信里——这是最常见的做法——打开后所有首帧图全是裂的。 而首帧图恰恰是这个报告最直观的部分。

怎么办：把首帧图以 base64 内联进 HTML（单文件会变大，但能保证"发到哪都打得开"），或者在报告页明确提示"必须整个文件夹一起发送"。前者更符合"离线报告"这个承诺。

11. 空间不足只提醒，不拦

创建任务时如果发现目标盘装不下，软件会记一条日志、界面上给个黄色提示，但仍然允许开始。 结果是拷到一半盘满，该盘被隔离，任务以"完成（有失败）"收场。

从"现场不能被软件拦死"的角度，不硬拦是有道理的（源盘可能比预估的还大）。 但对一个新用户，"你告诉我空间不够、我点了继续、结果拷失败了" 的体验会很差。

怎么办：保留"允许继续"，但把空间不足升级成需要明确勾选确认的对话框，并写清楚"该盘可能在拷到一半时被隔离"。

12. 日志按天累积，永不清理

日志按天分文件写在用户目录下，但没有任何清理或轮转策略。 日常使用量不大，属于慢性问题——但如果用户不主动删，两三年后就是一堆没人看的文件。

怎么办：启动时顺手删掉 30 天前的日志文件（保留当次任务相关的），或加个"日志保留天数"设置。

P2让它更像一个"产品"

这些不影响它能不能用，影响的是别人觉得它专不专业，以及你日后维护的成本。

交付与维护类

没有自动更新。软件改进了，用户不会知道，你还得挨个通知他重新下载。 对一个要分发给多人使用的工具，这是长期成本最高的一项。

没有持续集成。现在每改一次都要在本地手跑一遍完整验证，而那个一键验证命令本身在受限环境下还会崩（需要手动改环境变量才能跑）。 把它放到云端自动跑，能省掉大量重复劳动。

没有版本更新记录。开源项目里，别人想知道"这个版本改了什么"只能翻代码。慢慢补一份变更日志。

没有崩溃反馈入口。现在用户遇到问题唯一的办法是把日志文件夹翻出来发给你。界面上加一个"导出诊断包"按钮（把当天日志和版本信息打成一个压缩包），会省下很多来回沟通。

顺序建议：先做"导出诊断包"（成本最低、立刻有用），自动更新等有稳定用户群之后再上。

兼容性类

只考虑了 Apple 芯片。我检查了打出来的成品，主程序是纯 arm64 架构。 影视行业里还有大量 Intel 芯片的 Mac（尤其是 Mac Pro 工作站），他们装不上。 解决方案是打"通用二进制"，两份指令集打进一个包，安装包会大一些但一个包通吃。

只支持 macOS。如果没有任何 Windows 的计划，那就把这一点在下载页写得非常清楚， 别让人下载了才发现。（顺带一提：包里的最低系统版本写的是 12.0，而文档说是 13+，两边也该对齐。）

判断：如果这个软件真的是给剧组用的，Intel 支持几乎不是可选项——很多后期机房的老机器就是 Intel。

现场功能类（都能显著提升"专业感"）

没有命名模板。现场常见需求是按机位、拍摄日、卷号自动组织文件夹结构 （比如 A机/2026-09-15/卡号），现在只能原样保留源目录结构。

没有"两次拷贝结果对比"。交接时经常要核对"这一份和那一份是不是一致"， 现在只能各自生成报告、人眼比对。

没有导出清单表格。除 MHL 和报告之外，有些后期流程要一份表格（CSV）方便导入表格软件核对。

没有首次运行的引导。第一次打开软件的用户不知道该先点哪。现在的帮助页写得不错， 但它藏在侧边栏里，新用户不一定会点进去。

怎么选：建议先从"命名模板"开始——它是现场呼声最高、也最能体现专业度的一项。

代码整洁度小问题

一处死代码：路径定义里有个 settingsFile 指向一个 settings.json， 但设置实际是存在数据库里的，这个字段没有任何地方使用。它会误导后来的人。

开发环境的 Node 版本要求写低了：文档要求 22.12 以上， 而数据库用到的那个内置模块在更早的版本是需要额外开关的。实际依赖 Electron 自带的运行时，影响有限， 但文档数字应该对齐。另外该模块目前仍被标记为"实验性"，这是长期需要留意的技术债。

界面层没有自动化测试。核心逻辑测得很充分（337 项），但界面只靠截图验证。 这一项投入产出比一般，可以排在最后。

建议的推进路线

按"每一阶段结束都能拿出来给人用"来划分，而不是按技术模块。

阶段一 · 让它能被别人装上

目标：把一个安装包发给同事，他能装上、能打开、能拷卡
  1. 初始化 git 仓库，提交现有代码（地基，先做）
  2. 补 LICENSE 与第三方组件声明
  3. 做一套应用图标（1024×1024，打包工具会生成各尺寸）
  4. 写打包配置：应用标识、分类、Intel + Apple 双架构
  5. 把两个下载源镜像写进打包命令（已实测：配好即可在 38 秒内出包）
  6. 把 FFmpeg 的分发策略定下来，并让文档与实际一致
  7. 换一台干净的机器（或清空本机 ffmpeg）装一次，确认别人装完到底是什么体验

阶段二 · 让它能安心给别人用

目标：不用在旁边解释，同事自己就能用明白
  1. 买开发者证书，做签名和公证（解决"无法验证开发者"）
  2. 修掉那个假设置开关（要么做实，要么撤掉）
  3. 把"一个文件冲突 → 整盘停摆"改成只影响那一个文件
  4. 报告 HTML 改成单文件自包含
  5. 加"导出诊断包"按钮

阶段三 · 让它像个成熟产品

目标：公开分发、有人主动下载、你能持续迭代
  1. 加"仅校验"模式
  2. 打通用二进制，支持 Intel Mac
